Installation into an empty or existing environment (4.3 and 6.1)

Run from the project root after uv sync --dev:

uv run package-manager install examples/requests_example.txt --repo examples/repo_example.json --state examples/state_example.txt --output result.txt

repo_example.json, state_example.txt and requests_example.txt are the original
files supplied by the instructor.

The original requests_example.txt asks for both app==2.0 and tool.
Expected: no solution (exit code 1), because app 2.0 requires lib >=2.0,
whereas every version of tool requires lib <2.0. State and output are unchanged.

The separate successful install app==2.0 scenario described in section 6.1 is
covered by test_install_app_2_example_from_instruction. That test creates its
own temporary request file containing only app==2.0.

Expected changes:
Upgrade app: 1.0 -> 2.0
Upgrade lib: 1.0 -> 2.0
Remove tool==1.1
Install util==2.0

Resulting state:
app 2.0 manual
json-slow 1.0
lib 2.0
util 2.0

The previously installed json-slow is retained: installation minimizes removals.
Requested app is manual; tool is removed, so its manual marker disappears.

For an empty environment, omit --state:

uv run package-manager install examples/requests_example.txt --repo examples/repo_example.json --output result.txt

These same conflicting requests also have no solution in an empty environment.
Requests come exclusively from a file, with one requirement per line.

--state reads the current state. --output chooses a separate destination.
If --output is omitted, an existing --state file is updated after success.
Without either option, the result is printed without saving a file.
No solution or invalid input leaves the state/output files unchanged.

Existing-state installation minimizes, in order: removed packages, version
changes in retained packages, obsolescence of new requested packages, new
package count, and obsolescence of other new packages. Empty-state installation
uses the original 4.3 criteria: requested obsolescence, package count, other
obsolescence. Retained manual markers are preserved; requested packages become
manual. Every solver result is checked by the direct validator.

Exit codes: 0 success, 1 no solution, 2 invalid input/output or validation error,
3 solver unknown. Unknown is reported separately from no solution.

Tests: uv run pytest

Required group experiments (4.5; raw measurements, not the report):

uv run python -m src.experiments --data data --group 16 --output results/group16.json

This runs N = 10, 30, 100, 300, 1000. data/ matches repos/k16/ in the
instructor's repos.zip after normalizing Windows/Linux line endings.
Input SHA-256 hashes in the results also normalize these line endings.
The group number in each repository is checked before running it.

results/group16.json records the requests, version/axiom counts, outcome,
installed state, obsolescence, direct verification and measured times.
build_seconds includes repository loading/validation and knowledge-base
construction. solve_seconds includes the installation solver call, model
extraction and mandatory result verification. The optional extra direct
verification used to record validation_errors is outside that measurement.
For no solution, state-related fields are null: no state exists to verify.

The experiment command saves each completed case before starting the next;
a complete required run contains all five sizes. Missing dependencies in
repository versions produce the required warnings and are not input errors.
